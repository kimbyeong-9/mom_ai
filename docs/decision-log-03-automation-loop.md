# 결정로그 03 — Automation Loop 전환율 개선

## 주제

Automation Loop 전환율 개선

## 관련 지표

| 지표 | 목표 방향 |
|------|-----------|
| AP1 | Save → Automation Connected 전환율 ↑ |
| AP2 | Automation Connected → Automation Executed 전환율 ↑ |
| Automation_LCP | Automation Loop 완료율 ↑ |
| Automation_AR | Automation 실행 성공률 ↑ |

---

## 결정 사항

### 1. 자동화 연결 추천 구조

**결정**: 저장된 플랜의 각 단계에서 자동화 가능한 항목을 AI가 탐지하고 인라인으로 추천한다.

**근거**:
- 사용자가 자동화 기능의 존재를 인지하지 못하면 AP1이 발생하지 않는다
- 플랜 단계 내에서 맥락과 함께 추천하면 인지율이 높아진다

**제약**:
- MVP에서는 자동화 유형을 3가지로 제한한다  
  (알림 설정 / 문서 자동 정리 / 체크리스트 자동 생성)

---

### 2. 원클릭 실행 기능

**결정**: 연결된 자동화를 단 한 번의 클릭으로 실행할 수 있도록 설계한다.  
실행 결과는 Automation 페이지에서 상태로 확인한다.

**근거**:
- 자동화 연결 이후 실행까지 단계가 많으면 AP2가 낮아진다
- 원클릭 실행은 마찰을 최소화하여 AP2를 직접 개선한다

**제약**:
- 실행 전 확인 다이얼로그를 한 번 표시하여 실수 실행을 방지한다
- 실행 결과(성공 / 실패)를 명확히 피드백해야 한다

---

## 기능 구현 우선순위

1. 자동화 추천 컴포넌트 (플랜 단계 내 인라인)
2. 자동화 연결 UI (유형 선택 → 연결 확인)
3. Automation 페이지 — 연결된 자동화 목록
4. 원클릭 실행 버튼 + 실행 상태 표시

---

## 검증 방법

| 지표 | 측정 방법 |
|------|-----------|
| AP1 | 자동화 연결 완료 이벤트 / 저장 이벤트 |
| AP2 | 자동화 실행 이벤트 / 자동화 연결 이벤트 |
| Automation_LCP | AP1 × AP2 |
| Automation_AR | 자동화 실행 성공 이벤트 / 실행 시도 이벤트 |

---

## 개정 — 2026-07 (n8n 기반 지속 실행 구조로 전환)

### 배경

지금 백엔드(`automations.service.ts`)의 실행 로직은 전부 즉시 계산되는 가짜 로직이다 —
`notification` 타입은 알림을 실제로 보내지 않고 날짜만 계산하고, `document` 타입은 정규식으로
서류명만 추출한다. 외부 세계와 실제로 상호작용하지 않아 "연결했더니 진짜로 뭔가 일어난다"는
느낌이 없다.

### 결정 변경

- **2번 결정("원클릭 실행") 개정**: 1회성 실행 개념을 유지하되, 그 실행 엔진을 n8n으로
  교체한다. 백엔드는 자동화의 상태·이벤트(`automation_connected`, `automation_executed`,
  `automation_execution_succeeded`)만 계속 소유하고, 실제 폴링/검색/알림 발송은 n8n 워크플로우가
  담당 — 연결(connect) 시 웹훅으로 워크플로우를 트리거하고, n8n이 스케줄 실행 후 결과를
  백엔드 웹훅(`POST /automations/:id/results`)으로 콜백하는 구조.
- **자동화 유형 우선순위 재정의**: MVP 3유형(알림/문서정리/체크리스트) 중 두 버티컬에 맞춰
  아래 순서로 실제화한다.
  1. **채용/원격구인 모니터링** — 기존 `notification` 타입을 재정의. 사용자가 고른 국가/직군/
     원격여부 조건에 맞는 채용공고가 새로 올라오면 알려주는 자동화. 핵심 차별점이라 최우선.
  2. **비자·체류 마감일 리마인더** — 기존 `extractDeadlineDate` 로직은 이미 있으니, 계산만
     하고 끝나던 걸 n8n 스케줄로 실제 발송까지 잇는다.
  3. `document`(서류 정리) 타입은 외부 상호작용이 없어 n8n 없이 지금 로직 그대로 유지.

### 상태

설계만 합의됨, 아직 구현 시작 전 (2026-07-20 기준). n8n 인스턴스 준비와 웹훅 계약(연결 시
페이로드, 콜백 스펙)부터 정의해야 한다.

## 개정 — 2026-07-22 (구현 완료, 아키텍처 일부 변경)

### 배경

구현하면서 위 "결정 변경"에서 계획한 대로 n8n 워크플로우 안에 검색·중복 제거·매칭 계산 로직을
직접 넣으려 해보니, n8n의 노드 기반 UI로는 이 로직을 짜고 테스트하기가 어려웠다. 워크플로우
노드는 버전 관리도 안 되고, 단위 테스트도 불가능하다.

### 결정 변경

- **n8n의 역할을 스케줄 트리거로만 한정**한다. n8n 워크플로우는 정해진 주기로
  `POST /internal/automation-checks/run`(내부 전용, `X-Internal-Secret` 헤더로 보호)을
  호출하는 것 외에는 아무 로직도 갖지 않는다.
- **검색·중복 제거·매칭 계산은 전부 NestJS(`AutomationsService.recheckMonitoringAutomations`)
  안에 남긴다.** 이렇게 하면 이 로직을 일반 TypeScript 코드로 작성·테스트·리팩터링할 수 있고,
  n8n은 순수하게 "정해진 시간에 한 번씩 깨워주는" 역할만 한다.
- 원래 계획했던 "연결 시 웹훅으로 트리거 → n8n이 폴링 → 결과를 `POST /automations/:id/results`로
  콜백"하는 구조는 채택하지 않았다. 콜백 왕복 대신 n8n → 백엔드 단방향 호출 하나로 충분했고,
  이쪽이 실패 지점이 적다.

### 결과

- 채용/원격구인 모니터링 자동화가 실제로 지속 실행되며, 매칭 건수(`matchCount`/
  `newMatchCount`)와 마지막 확인 시각(`lastCheckedAt`)을 실제 데이터로 표시한다
  (`AutomationLiveMonitorCard`).
- 비자·체류 마감일 리마인더는 `extractDeadlineDate`로 라벨에서 날짜를 추출해 계산하되, 아직
  실제 발송(이메일/푸시 등)은 붙이지 않았다 — 다음 확장 후보.
- `document`(서류 정리) 타입은 원래 계획대로 n8n 없이 정규식 기반 로직 그대로 유지.

### 개정 — 2026-07-22 (마감일 리마인더 실제 발송 구현)

같은 "n8n은 스케줄러, 로직은 백엔드" 패턴을 재사용해 실제 발송까지 연결했다. n8n이 매일
`POST /internal/automation-checks/deadline-reminders`를 호출하면, `AutomationsService`가
D-7/D-1/D-0 중 하나에 해당하는 자동화를 찾아 이메일을 보낸다.

이메일 발송 서비스는 처음 Resend를 검토했으나, **실제 수신자에게 보내려면 본인 소유 도메인을
Resend에 등록·인증(DNS 설정)해야 한다**는 걸 확인했다 — `onboarding@resend.dev`로는 Resend가
지정한 테스트 주소(`delivered@resend.dev` 등)에만 보낼 수 있다. 포트폴리오 규모(발송량 적음,
실사용자는 개발자 본인)에서 도메인 구매·인증까지 가는 건 배보다 배꼽이라 판단해, 도메인 인증이
필요 없는 **Gmail SMTP(Nodemailer + 앱 비밀번호)**로 전환했다.

중복 발송 방지를 위해 `Automation.sentReminderMilestones: string[]`에 이미 보낸 마일스톤
(`'D-7'`/`'D-1'`/`'D-0'`)을 기록한다. 실제 계정으로 라이브 발송 테스트 완료 — 첫 호출은
`{checked: 1, sent: 1}`, 같은 자동화로 재호출 시 `{checked: 1, sent: 0}`으로 중복 방지 확인.
